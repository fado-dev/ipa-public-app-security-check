# インシデント対応チェック（CSIRT/CERT 観点）

NIST SP 800-61 / JPCERT/CC「インシデントハンドリングマニュアル」の流れに沿った確認項目。
各項目を ✅/⚠️/❌/❓ で記録し、インシデント対応中は**タイムライン**を更新し続ける。

> 期限・要否は業種・所在地・契約により異なる。ここに書く期限は一般的な目安であり、最終判断は法務・顧問弁護士・所管官庁に確認する。

---

## 平時の準備（Step 5 で使用）

### 体制・連絡
| # | 項目 |
|---|---|
| P-1 | インシデント対応責任者（意思決定者）と技術責任者が決まっている |
| P-2 | 連絡網（経営層、法務、広報、人事、委託先、クラウド/ホスティング事業者、セキュリティベンダー、顧問弁護士）が整備され、夜間休日の連絡手段がある |
| P-3 | 外部の専門ベンダー（フォレンジック・インシデントレスポンス）の連絡先と契約条件（緊急時の依頼手順）が把握されている |
| P-4 | 役割分担（指揮、技術調査、封じ込め実行、記録、広報・顧客対応、法務）が決まっている |
| P-5 | インシデント専用の連絡チャネル（侵害されたシステムとは独立した手段）が用意されている |

### 検知・判断
| # | 項目 |
|---|---|
| P-6 | 監視・アラート（WAF、IDS/IPS、クラウド監査ログ、認証失敗、異常トラフィック、ファイル改変）が設定され、誰が受け取るか決まっている |
| P-7 | 何をもってインシデントと判定するかの基準と、判定までの手順がある |
| P-8 | 深刻度の分類基準（影響範囲、データ種別、業務影響）と、それに応じたエスカレーション先がある |
| P-9 | 公的機関・ベンダーからの注意喚起・IOC を定期的に収集し、照合する運用がある |

### 証拠保全
| # | 項目 |
|---|---|
| P-10 | 各システムのログ（Web/AP/DB/認証/クラウド監査/WAF/VPN/EDR）の所在・保持期間・書き出し方法が把握されている |
| P-11 | ログの保持期間が調査に十分（最低 3 か月、推奨 1 年以上）で、改ざん防止（別アカウント・別ストレージへの転送）がされている |
| P-12 | ディスクイメージ・メモリダンプの取得可否と手順（クラウドならスナップショット）が把握されている |
| P-13 | 時刻同期（NTP）が全システムで行われ、タイムゾーンが統一または明記されている |

### 封じ込め・復旧
| # | 項目 |
|---|---|
| P-14 | 公開停止、IP 遮断、WAF ルール追加、アカウント無効化、トークン失効、ネットワーク遮断を**誰が・どの権限で・何分で**実行できるか決まっている |
| P-15 | 全シークレット（DB パスワード、API キー、署名鍵、OAuth クライアントシークレット、サービスアカウント）の一覧と、ローテーション手順がある |
| P-16 | バックアップが複数世代あり、本番から隔離（別アカウント・イミュータブル）されている |
| P-17 | バックアップからの復元テストを実施した実績がある（復旧目標時間が把握されている） |
| P-18 | クリーンな構成から再構築できる（IaC、コンテナイメージ、ゴールデンイメージ） |

### 報告・通知
| # | 項目 |
|---|---|
| P-19 | 報告先と期限の一覧（下記「報告・通知先」）が整備されている |
| P-20 | 個人情報保護委員会への報告様式、顧客通知文、公表文のテンプレートがある |
| P-21 | 問い合わせ窓口（コールセンター、専用メール）を短時間で立ち上げられる |
| P-22 | 取引先・委託元との契約上の報告義務（期限、方法）が把握されている |

### 脅迫・二次被害
| # | 項目 |
|---|---|
| P-23 | 脅迫（データ公開をほのめかす連絡、身代金要求）を受けた場合の対応方針（支払わない方針、警察相談、接触しない）が事前に決まっている |
| P-24 | 漏えいを想定し、顧客に MFA 設定・パスワード変更・フィッシング注意を呼びかける文面と手段がある |

### 訓練
| # | 項目 |
|---|---|
| P-25 | 机上演習（テーブルトップ）を年 1 回以上実施している |
| P-26 | 過去のインシデント・ヒヤリハットの振り返りが対応手順に反映されている |

## フェーズ別チェック（Step 6 で使用）

### Phase 1. 検知・トリアージ
| # | 項目 |
|---|---|
| IR-1 | 検知の内容（何を・いつ・どこで・誰が・どの手段で）を記録した |
| IR-2 | タイムラインの記録を開始した（時刻は UTC/JST を明記、以後すべての行動・判断・連絡を追記） |
| IR-3 | 対応責任者を指名し、関係者に第一報を出した（侵害された可能性のあるチャネルは使わない） |
| IR-4 | 影響を受けうるシステム・アカウント・データの範囲を暫定的に特定した |
| IR-5 | 深刻度を暫定判定し、エスカレーション（経営層、法務）の要否を決めた |
| IR-6 | 専門ベンダー（フォレンジック）への調査依頼を検討・依頼した |
| IR-7 | 攻撃が継続中かどうかを判断した（継続中なら封じ込めを優先） |
| IR-8 | 対応に使う端末・アカウントが侵害されていないことを確認した |

### Phase 2. 証拠保全
| # | 項目 |
|---|---|
| IR-9 | ログのローテーション・自動削除を止めるか、対象期間のログを別の場所に書き出した |
| IR-10 | 書き出したログ・ファイルのハッシュ（SHA-256）を記録し、取得日時・取得者を記録した |
| IR-11 | 侵害が疑われるホストのディスクイメージ・スナップショット・メモリダンプを取得した（再起動・再構築の前に） |
| IR-12 | Web シェルや不審ファイルは削除せず、コピーを保全した（実行しない） |
| IR-13 | クラウド監査ログ（CloudTrail 等）、WAF/CDN ログ、認証基盤（IdP）のログを対象期間分確保した |
| IR-14 | 外部サービス（SaaS）側のログは保持期間が短い場合があるため、早期にエクスポートを依頼した |
| IR-15 | 証拠の取り扱い記録（誰が・いつ・何を・どこへ）を残した（チェーン・オブ・カストディ） |

### Phase 3. 封じ込め
| # | 項目 |
|---|---|
| IR-16 | 侵害経路（該当機能・エンドポイント・サーバ）を遮断または公開停止した |
| IR-17 | 攻撃元 IP の遮断、WAF ルールの追加を行った（IP は変わる前提で、恒久対策ではないと認識） |
| IR-18 | 侵害された、または侵害が疑われるアカウントを無効化し、セッションを失効させた |
| IR-19 | 侵害されたシステムが持つ全シークレット（DB、API キー、署名鍵、OAuth、サービスアカウント、SSH 鍵）をローテーションした |
| IR-20 | 同一の認証情報・鍵を使う他システムを特定し、横展開の有無を確認した |
| IR-21 | 攻撃者が気づいて証拠を消したり活動を加速したりしないよう、封じ込めの順序と同時実行を計画した |
| IR-22 | 侵害ホストをネットワークから隔離した（電源は切らない。メモリ上の証拠を保つ） |
| IR-23 | 封じ込め後も攻撃が続いていないかを監視した（別経路、別アカウント） |

### Phase 4. 根絶
| # | 項目 |
|---|---|
| IR-24 | 侵入経路（脆弱性、設定不備、漏えいした認証情報）を特定し、修正した |
| IR-25 | Web シェル、不正ファイル、不正アカウント、不正な API キー・OAuth 連携を除去した |
| IR-26 | 永続化の痕跡（cron、systemd、起動スクリプト、SSH authorized_keys、新規ユーザー、sudoers、不審プロセス、スケジュールタスク）を確認・除去した（`scripts/check_persistence.sh`） |
| IR-27 | 侵害されたホストはクリーンなイメージから再構築した（修正だけで済ませない） |
| IR-28 | 同じ脆弱性・設定不備が他のシステムにないか横展開で確認した |
| IR-29 | バックアップ自体が侵害・暗号化されていないことを確認した |

### Phase 5. 復旧
| # | 項目 |
|---|---|
| IR-30 | クリーンなバックアップまたは再構築した環境から復旧した |
| IR-31 | 復旧前に脆弱性修正・設定変更・シークレットローテーションが完了していることを確認した |
| IR-32 | 復旧後の監視を強化し（アラート閾値、ログ確認頻度）、確認期間（例: 2 週間〜1 か月）を設定した |
| IR-33 | 段階的に公開範囲を戻し、各段階で異常がないことを確認した |
| IR-34 | 利用者への影響（サービス停止、パスワードリセット要請）を周知した |

### Phase 6. 影響範囲の特定
| # | 項目 |
|---|---|
| IR-35 | アクセスされた・持ち出された可能性のあるデータの種類・項目・件数・対象者を特定した |
| IR-36 | 攻撃者がアクセス可能だった期間（初回侵入〜封じ込め）を特定した |
| IR-37 | データ持ち出しの証跡（大量レスポンス、外部への転送、DB のダンプ）を確認した |
| IR-38 | 二次被害の可能性（なりすまし、不正利用、フィッシング、他サービスへのリスト型攻撃）を評価した |
| IR-39 | 取引先・委託元・委託先のデータが含まれるかを確認した |
| IR-40 | 「特定できない」場合は、最大の範囲を前提に報告・通知する方針を決めた |

### Phase 7. 報告・通知
| # | 項目 |
|---|---|
| IR-41 | 個人情報保護委員会への報告要否を判断し、速報・確報を期限内に行った |
| IR-42 | 所管官庁（業法による）への報告要否を確認した |
| IR-43 | 警察（都道府県警察サイバー犯罪相談窓口）に相談・被害届を検討した |
| IR-44 | JPCERT/CC へのインシデント報告、IPA への届出を行った |
| IR-45 | 本人（顧客・利用者）への通知を行った（または公表で代替する判断をした） |
| IR-46 | 取引先・委託元への契約上の報告を行った |
| IR-47 | 公表の要否・時期・文面を経営層・法務・広報で決定した（上場企業は適時開示の要否も確認） |
| IR-48 | 問い合わせ窓口を設置し、想定問答を準備した |
| IR-49 | 脅迫を受けた場合、攻撃者と接触せず、警察に相談した |

### Phase 8. 事後対応
| # | 項目 |
|---|---|
| IR-50 | 根本原因分析（技術的要因・運用的要因・組織的要因）を行った |
| IR-51 | 再発防止策を策定し、期限と担当を決めた |
| IR-52 | 対応の振り返り（検知までの時間、封じ込めまでの時間、うまくいった点、改善点）を行った |
| IR-53 | IOC（IP、UA、ファイルハッシュ、手口）を JPCERT/CC 等に共有した |
| IR-54 | 平時の準備（P-1〜P-26）の不備を更新した |
| IR-55 | 最終報告書を作成し、経営層に報告した |

## 報告・通知先（日本国内の一般的な目安）

| 報告先 | 対象 | 期限の目安 | 備考 |
|---|---|---|---|
| 個人情報保護委員会 | 個人データの漏えい等（要配慮個人情報、財産的被害のおそれ、不正目的によるおそれ、1,000 人超 のいずれか） | 速報: 発覚から概ね 3〜5 日以内 / 確報: 30 日以内（不正目的によるおそれの場合は 60 日以内） | 本人への通知も必要。https://www.ppc.go.jp/ |
| 本人（顧客・利用者） | 同上 | 速やかに | 通知が困難な場合は公表等の代替措置 |
| 所管官庁 | 業法で報告義務のある事業者（金融庁、総務省（電気通信事業者）、経産省 等） | 業法・ガイドラインによる | 金融機関は金融庁の監督指針、通信事業者は通信の秘密漏えいの報告義務 等 |
| 警察 | 不正アクセス、脅迫 | 速やかに | 都道府県警察サイバー犯罪相談窓口。被害届の提出を検討 |
| JPCERT/CC | インシデント全般 | 任意、速やかに | https://www.jpcert.or.jp/form/ 。IOC 共有・調整支援 |
| IPA | コンピュータウイルス・不正アクセスの届出 | 任意 | https://www.ipa.go.jp/security/todokede/crack-virus/index.html |
| 取引先・委託元 | 契約上の報告義務 | 契約による | 委託先として受託データが含まれる場合は特に注意 |
| 証券取引所 | 上場企業で投資判断に影響する場合 | 適時開示 | 法務・IR に確認 |
| クレジットカードブランド・アクワイアラ | カード情報の漏えい | 契約による | PCI DSS の要件 |

## タイムラインの記録様式

```
| 日時 (JST) | 事象 / 行動 | 実施者 | 根拠・証跡 |
|---|---|---|---|
| 2026-10-11 09:12 | WAF アラート: /api/admin/users への 401 連続 | 監視チーム | WAF ログ #12345 |
| 2026-10-11 09:30 | インシデント判定、対応責任者に A を指名 | CTO | Slack #ir-20261011 |
```

- 事実と推測を分けて書く（推測は「〜の可能性」と明記）
- 時刻の出典（ログの時刻かシステム時計か）を明記する
- 判断の根拠と判断者を残す（後の報告・振り返りに使う）
